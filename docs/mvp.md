# Границы первой итерации

Это исторические решения первоначального каркаса. Актуальная сверка с оригиналом
ТЗ, включая реальные данные, LLM, проживание и перелёты: [requirements-audit.md](requirements-audit.md).
Ограничения Demo City и первоначальные «следующие итерации» ниже не описывают
текущую полную функциональность приложения.

## Принятые правила

- Один город, 1–14 дней, 1–6 участников; основной демо-сценарий — два участника.
- Бюджет общий, в EUR, хранится целым числом евроцентов. По умолчанию ограничивает
  остановки; опциональный режим включает пользовательские оценки жилья и транспорта,
  резерв и выбранные заказы питания. Неуказанные расходы не считаются бесплатными.
  Поиск предложений и бронирование не выполняются; подробности — meals-budget.md.
- Веса категорий каждого участника: 0–1, пропущенная категория имеет вес 0.
- Обязательные и запрещённые места задаются для группы. Совпадение — конфликт,
  который нужно разрешить пользователю; система не снимает запрет автоматически.
- Все цены, часы и переезды в демо синтетические. Реальная география не заявляется.
- Сначала планируется маршрут без LLM. Объяснения позже строятся по вычисленным фактам.

## Архитектура

Модульный монолит: HTTP → входные схемы → сценарий планирования → алгоритмическое ядро.
Адаптеры данных поставляют POI и матрицу перемещений, хранилище обслуживает профили
и сохранённые маршруты. Ядро planning не импортирует HTTP, ORM или SDK LLM.

Реализованы User, Group, Membership, TripRequest, RouteSet и RouteOption. Предпочтения хранятся
в Membership как профиль в контексте группы, посещения — внутри JSON результата RouteOption.
TripRequest содержит неизменяемый снимок участников и предпочтений. Отдельные сущности
POI, Visit и персональный профиль вне группы вводятся в следующих итерациях.

## Порядок следующих итераций

1. Запустить PostgreSQL, применить миграцию, проверить подключение.
2. Группы, предпочтения, сохранение запроса и результата с миграциями реализованы.
3. Независимая финальная проверка реализована в `planning/validator.py` и подключена
   к обоим эндпоинтам расчёта. Beam search и сравнение с greedy реализованы;
   результаты шести синтетических сценариев — в `algorithm-comparison.md`.
4. Подключить POI и routing через адаптеры, добавить происхождение и актуальность данных.
5. Redis TTL-кэш OSM/OSRM и обработка отказов реализованы (redis-cache.md).
6. LLM-ввод и проверяемые объяснения реализованы локально через llama.cpp (llama-cpp.md).
   Карта дневных сегментов реализована на MapLibre (route-map.md).
7. Многодневное планирование, начальное расширение каталога, альтернативы и сравнение
   реализованы (multiday.md, catalog-v2.md, alternatives.md). Статические визовые
   требования и предупреждения о сроках реализованы для Португалии и семи гражданств
   (visa-rules.md). Карта и приёмочные сценарии реализованы (acceptance.md).
   Версионное хранение и атомарное обновление реального каталога реализованы
   (versioned-catalog.md). Добавлены три кафе и два места природы (catalog-food.md).
   Живой LLM проверен; исправления разбора и границы оценки описаны в
   llm-parser-grounding.md. Далее — независимые новые формулировки, качество поиска
   и показатели полного сценария.
   Семантический поиск и Qdrant реализованы (semantic-retrieval.md, qdrant.md).

## Критерии приёмки каркаса

- `/health` отвечает, Swagger содержит demo endpoint.
- Два участника получают воспроизводимый маршрут на фиксированных данных.
- Проверяются бюджет, часы работы, длительность, переезды и обязательные POI.
- Недопустимый маршрут не маркируется выполнимым.
- Тесты и lint проходят. Миграция генерирует SQL и применяется на PostgreSQL при доступном Docker.
