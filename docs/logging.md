# Структурированное логирование

Этап `feature/structured-logging` основан на `feature/route-map-acceptance`.
В исходном PDF ТЗ: NFR-12 (страница 7) — JSON INFO/WARN/ERROR с корреляционным ID;
технологическая таблица (страница 10) допускает structlog или стандартный logging + JSON.
Выбран стандартный `logging`: общий обработчик событий Python/Uvicorn, явный формат
и фильтр разрешённых метаданных. Новые зависимости и миграции не требуются.

## Запуск и расположение

Из `backend`:

```powershell
.\.venv\Scripts\python.exe -m app.run --reload
```

Штатный backend — `127.0.0.1:8001`, Swagger `/docs`, liveness `/health`.
Без перезагрузки: `python -m app.run`. Порт задаётся `--port 8001`.
Этот запуск настраивает JSON до запуска Uvicorn. Прямой `uvicorn app.main:app` тоже
получит JSON после импорта приложения; ранние сообщения его reload-supervisor могут
оставаться текстовыми. Поэтому основной документированный запуск — `app.run`.

Настройки `.env` в корне проекта:

```dotenv
LOG_LEVEL=INFO
LOG_FILE=.local/logs/backend.log
LOG_MAX_BYTES=5000000
LOG_BACKUP_COUNT=3
```

Путь относителен к корню проекта, независимо от текущего каталога. По умолчанию JSON
выводится в stderr и записывается в файл UTF-8. `LOG_FILE=` в `.env` отключает файл.
Размер ротации — 5 MB, три резервные копии: `backend.log.1`–`.3`; около 20 MB на
семейство, без учёта отдельной очень большой записи. Каталог и резервные логи
исключены из Git. При невозможности открыть файл сохраняется консоль; при сбое
записи выводится безопасное `logging.write.failed`, без дампа сообщения/аргументов.

Смотреть из корня проекта:

```powershell
Get-Content .\.local\logs\backend.log -Tail 20 -Wait
```

Файловая ротация рассчитана на один пишущий процесс. При `--reload` родитель пишет
только в консоль, файл ведёт обслуживающий дочерний процесс. Для нескольких workers
использовать консоль и внешний сборщик либо отдельные файлы. Не запускать несколько
копий API с одним LOG_FILE. Скрипты оценки и индексации автоматически используют
суффиксы `backend-llm-evaluation.log`, `backend-retrieval-evaluation.log`,
`backend-catalog-index.log`, чтобы не конкурировать с API за файл.

## Формат и корреляция

Одна запись — одна JSON-строка: `schema_version`, UTC `timestamp`, `level`, `service`,
`process_id`, `logger`, `event`, `request_id`, затем разрешённые поля события.
В JSON уровень предупреждения называется `WARN`; настройка принимает WARN и WARNING.
События запуска/остановки имеют `request_id=null`, поскольку не относятся к HTTP-запросу.

Каждый HTTP-запрос получает UUID. Канонический UUID из `X-Request-ID` принимается;
отсутствующие, повторённые, невалидные и слишком длинные значения заменяются.
ID возвращается в ответах, включая 404/422/503/500, и передаётся адаптерам OSM/OSRM,
llama.cpp, embeddings и Qdrant. Их серверы сами решают, как обрабатывать этот заголовок.
Next.js передаёт ID в обе стороны; при ошибке UI показывает «Код запроса: …».
При отказе соединения с backend прокси может сформировать собственный 502 с ID;
такого запроса в логах backend не будет, поскольку он туда не поступил.

Контекст хранится в `ContextVar`, middleware — pure ASGI. Синхронные обработчики
FastAPI получают его в thread pool; параллельные запросы изолированы. Контекст
сбрасывается после завершения, исключения и отмены; потоковые ответы учитываются
после передачи последнего блока. Стандартная access-строка Uvicorn отключена, чтобы
не дублировать событие и не записывать IP, полный URL и query string.

Найти цепочку из корня:

```powershell
$reply = Invoke-WebRequest http://127.0.0.1:8001/health
$rid = $reply.Headers['X-Request-ID']
Get-Content .\.local\logs\backend.log | ForEach-Object { $_ | ConvertFrom-Json } | Where-Object { $_.request_id -eq $rid }
```

По умолчанию каждый HTTP-запрос получает новый ID. Клиент, передающий собственный
X-Request-ID, отвечает за его уникальность. Последующие действия пользователя
(расчёт, объяснение, история) имеют разные ID; числовые trip/route/route_set ID связывают
сохранение. ID не подтверждает личность пользователя и не заменяет авторизацию.

## События

| Группа | Что видно |
| --- | --- |
| `server.*` | Запуск, готовность, перезагрузка и остановка Uvicorn |
| `http.request.*` | Метод, шаблон маршрута, статус, длительность; сбой/отмена/незавершённый ответ |
| `cache.read/write` | OSM/OSRM, hit/miss/invalid/unavailable/stored/skipped, TTL и возраст hit |
| `upstream.request.*` | Источник, номер попытки, HTTP-статус или тип ошибки, длительность, будет ли повтор |
| `upstream.response.rejected` | Некорректный ответ источника, не попавший в кэш |
| `catalog.loaded`, `planning.data.*` | Число дней/POI/кандидатов, источник данных и время подготовки |
| `planning.solve.*` | Алгоритм, участники/дни, допустимость, число вариантов/визитов, статус CP-SAT, время |
| `route.saved`, `route_set.saved` | ID результата после успешного коммита БД |
| `llm.call.*`, `llm.output.rejected` | Модель, операция, время, попытка, token usage при наличии; отклонение схемы/фактов |
| `assistant.parse.*`, `explanation.*` | Число уточнений, сохранение/повторное чтение объяснения, llm/template и причина fallback |
| `embeddings.batch.*`, `qdrant.*`, `retrieval.search.*` | Размер партии, размерность, статусы/ошибки/длительность, число найденных мест |

Повторы, TTL и алгоритмы этим этапом не перенастраиваются. Статус UNKNOWN по-прежнему
означает отсутствие найденного решения за лимит, а не доказанную невозможность.

## Какие данные исключены

В JSON попадает белый список полей и значений. Не записываются тела запросов/ответов,
свободные сообщения logger, заголовки авторизации/cookies, полные URL и query string,
координаты, имена/документы участников, предпочтения, промпты, ответы LLM, векторы,
строки подключения, SQL и параметры запросов. Для неизвестного маршрута пишется
`<unmatched>`; известные маршруты представлены шаблонами, например `/api/v1/groups/{group_id}`.

Вместо текста исключения сохраняются классы ошибок/цепочки причин, числовой errno
при наличии и ограниченные stack frames: файл, функция, строка. Исходные строки кода,
locals и сообщения причин не сериализуются. Это снижает подробность свободных
сообщений библиотек; детализацию добавляют явными безопасными полями событий.

Отдельный llama-server, Docker и внутренние сообщения Next.js сохраняют собственный
формат. Здесь описаны Python backend/утилиты и передача HTTP ID через Next.js.
Это технические диагностические логи, а не реализация журнала аудита FR-26 или
системы метрик/распределённой трассировки. Файлы локальные, права доступа задаёт ОС.

## Проверки и фактический прогон

- Тесты проверяют параллельные sync/async запросы, заголовки и очистку контекста,
  потоковый ответ, HTTP-ошибки/500/отмену, скрытие canary-данных, повторы/кэш,
  отбраковку LLM-ответа, template fallback, ротацию, недоступный файл и сбой записи.
- Живой backend на 8001: `/health`, `/docs`, 404, расчёт CP-SAT — ID и события
  корректны. Настоящая Qwen3-4B через llama.cpp вернула распознанный запрос за
  примерно 15,7 с: один ID у `llm.call`, `assistant.parse` и HTTP-ответа. Это проверка
  логирования одного примера, не новая оценка качества модели.
- В ограниченной среде запуска OSM вернул 503 с двумя `connect_error`. Повтор после
  запуска обычного процесса без ограничений среды получил 200 примерно за 6 с.
  Следовательно, первый результат сам по себе не доказывает недоступность сервиса OSM.
- Отдельный живой вызов адаптера получил OSM из Redis и OSRM HTTP 200, сохранил
  матрицу в Redis: 3 пригодных POI и 12 записей времени для выбранной даты. Этот
  технический прогон не создавал пользователей или маршрутов в БД.
- В runtime-JSON не найден контрольный canary, переданный в URL, заголовке и теле
  запроса. Тестовые журналы и локальные протоколы в Git не включаются.
- Проверена штатная связка frontend 3001 → backend 8001: успешный расчёт и ошибка
  чтения сохраняют X-Request-ID через Next.js. Собственные временные копии на
  3002–3004/8002–8004 остановлены. Полный набор: 281 backend-тест и 10 frontend-тестов,
  production-сборка Next.js, Ruff, проверка миграций и lock-файла.

[RotatingFileHandler](https://docs.python.org/3.13/library/logging.handlers.html#rotatingfilehandler),
[логирование Uvicorn](https://uvicorn.dev/concepts/logging/).
