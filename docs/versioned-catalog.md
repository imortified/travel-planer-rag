# Версии и обновление каталога POI

Актуальное расширение на три города, PBF-выгрузку и 24 кандидата в день:
[portugal-catalogs.md](portugal-catalogs.md). Ниже описан исходный этап одного города.

Этап `feature/versioned-catalog` основан на `feature/structured-logging`.
С 24 октября 2026 API читает опубликованный каталог PostgreSQL. Чтение списка мест
и планирование не загружают OSM заново. Это отделяет доступность источника от расчёта
и сохраняет точное происхождение использованной версии.

## Запуск и обновление

Из корня запустить `docker compose up -d --wait`. Из `backend`:

```powershell
.\.venv\Scripts\python.exe -m alembic upgrade head
.\.venv\Scripts\python.exe refresh_catalog.py
.\.venv\Scripts\python.exe refresh_catalog.py --status
.\.venv\Scripts\python.exe -m app.run --reload
```

`0009` добавляет три таблицы. Первоначальная публикация обязательна для Lisbon;
Demo City работает отдельно. Обновление запускается той же командой вручную;
фонового планировщика пока нет. Команда обновления требует PostgreSQL и доступа к OSM.
Redis необязателен. `--status` читает активную версию и последние десять версий без сети.
Успех возвращает код 0 и JSON с `version_id`, `poi_count`, `content_sha256`, `reused`;
ошибка — код 1, безопасное описание и ID для поиска в JSON-логах.

## Хранение и публикация

| Таблица | Содержимое |
| --- | --- |
| `catalog_versions` | Направление, источник, исходная точка, атрибуция, время получения/публикации, срок свежести, версия ручного справочника, SHA-256, число POI |
| `catalog_pois` | Место в конкретной версии: имя, координаты, категория, цена или неизвестное значение, длительность, исходное правило часов, источники, provenance и причины ограничений |
| `catalog_heads` | Указатель на активную версию направления |

1. Загрузить и проверить `data/lisbon-curated.json`, затем получить свежий OSM.
   Обновление обходит чтение Redis; существующий XML не получает новое время получения.
2. Проверить координаты, цены, ID, расписания и происхождение. Пустой исходный OSM,
   дубликаты и некорректные факты не публикуются. Неизвестные цена/часы сохраняются
   как неизвестные, такие места исключаются из расчёта.
3. В одной транзакции заблокировать указатель направления, записать версию и все POI,
   прочитать их обратно, проверить контрольную сумму и только затем переключить указатель.
   Сетевых запросов внутри этой транзакции нет.
4. Ошибка откатывает публикацию целиком. Читатели продолжают видеть предыдущую полную
   версию. Более старое время получения не может заменить уже опубликованное новое.

Одинаковый снимок с тем же временем получения не дублируется. Успешная повторная
загрузка с новым временем получения создаёт новую версию даже при тех же фактах.
Старые версии сохраняются. Обновление версий в приложении не предусмотрено;
контрольная сумма обнаруживает случайное изменение сохранённых данных. Это не
криптографическая защита от администратора БД, способного изменить и данные, и сумму.

## Свежесть и даты

`CATALOG_MAX_AGE_SECONDS=604800` — техническая политика максимального возраста
опубликованной загрузки: семь суток, допустимая настройка от одного часа до семи суток.
Это не гарантия актуальности цен и не Redis TTL. Изменение настройки действует на
следующую публикацию. Срок хранится в самой версии и при чтении не продлевается.

Ручные цены/часы имеют собственные `checked_on` и `valid_until`. Повторная загрузка OSM
не подтверждает эти факты и не продлевает их срок. Изменять их нужно после проверки
первоисточников в кураторском JSON, затем публиковать новую версию. Кураторские факты
допускаются только при действующей проверке сегодня и применимости на дату поездки.

Недельные правила `opening_hours` хранятся без готового дневного окна. Часы и причины
исключения вычисляются заново для каждого дня в местном времени Lisbon. Закрытые,
неподдерживаемые или разрывные интервалы не превращаются в круглосуточный доступ.

Каталог с истёкшим техническим сроком можно просмотреть: `status=expired`, POI имеют
`catalog_expired` и недоступны для нового расчёта. Новый расчёт возвращает 503 до вызова
OSRM. Отсутствующая/повреждённая версия или недоступная БД также дают 503.
Автоматическая подстановка живого OSM, демо-данных или продление сроков отсутствуют.

## Планирование и другие хранилища

Один экземпляр читателя фиксирует версию и время проверки на всю операцию:
все дни и варианты одного расчёта используют один снимок. `catalog_snapshot` содержит
ID, SHA-256, времена публикации/получения/истечения и версию ручных фактов.
Он возвращается в каталоге и сохраняется в `result.data_context` и дневных контекстах.
UI показывает свежесть загруженного каталога и версию, использованную в старом маршруте.
Старые результаты без этого поля продолжают открываться.

Матрицы OSRM остаются в TTL-кэше Redis на час. Новый расчёт требует свежую матрицу
из Redis либо доступный OSRM; опубликованный каталог устраняет только зависимость
от OSM при чтении/планировании. История результатов читается без OSM/OSRM.
Для OSM Redis хранит последний проверенный ответ (24 часа), но refresh принудительно
получает новый. Qdrant хранит векторы описаний; публикация POI не запускает индексацию
автоматически. `index_catalog.py` читает одну опубликованную версию на весь период.

Лимит кандидатов остаётся 12, содержимое кураторского слоя не расширено. В БД хранится
весь полученный каталог, включая исключённые места. Географический охват прежний:
OSM node центрального Lisbon и проверенные дополнения Ajuda. Нового HTTP-эндпоинта
обновления нет: управление пока локальное через CLI, авторизация в MVP ещё не реализована.

Новые тесты проверяют откат, конкурирующих писателей и чтение предыдущей версии
до commit, запрет устаревшей публикации, повреждение контрольной суммы, дневные
окна, истечение сроков, отсутствие OSM-вызовов при чтении и неизменность истории API.

полученными 2026-10-24T08:37:04Z, со сроком свежести до 2026-10-31T08:37:04Z.
Номер относится к этой локальной БД; в другой установке он может отличаться.
Алгоритмический слой и целевая функция не изменялись; повтор экспериментов CP-SAT
не требуется для проверки этого изменения хранения.

а не оценка оптимальности или полноты каталога.
