# Уточнение темы и неподтверждённых условий поиска

Ветка `fix/semantic-search-evidence` основана на `feature/rag-quality-evaluation`.
Политика ответа `semantic-evidence-v2`. Эмбеддинги, llama.cpp, коллекции, тексты
описаний и пороги 0.55 / 0.05 / 0.40 сохранены. Миграция БД не нужна.

## Аудит исходного результата

Первый отчёт RAG содержит 32 положительных запроса и восемь без подходящего
автоматического контекста. Категория назначена верно в 9/32 положительных случаях,
23 потребовали уточнения; неверных назначений не было. В двух отрицательных/неподтверждённых
запросах вернулись описания выше порога. Важно различать этот результат и UI:
интерфейс уже скрывал описания при `negative_or_complex`, но сервер продолжал
возвращать ранжирование, а прямой расчёт с `semantic_query` мог использовать его.
Для веганского запроса UI мог предложить ручную категорию и применение темы.

Эталоны исходных 40 запросов не изменены. Аудит подтверждает, что оценки 1 у
Casa dos Bicos и спортивного музея в широких исторических запросах опираются только
на название/категорию, а не на описание экспозиции. Это частичная текстовая поддержка,
не проверка коллекции. Экспертная независимая разметка ещё нужна. Ошибка судьи
на Карму (`rag-03`) описана в [rag-evaluation.md](rag-evaluation.md): требование
рассуждать вместо копирования reference не относится к Context Precision.

## Правила

- Одно явное тематическое пожелание может предложить категорию, если первое
  описание выше прежнего порога 0.40 принадлежит той же категории каталога.
  Используется небольшой словарь четырёх тем, а не понимание произвольного текста.
- Без явной темы остаётся прежняя проверка профиля: cosine >= 0.55 и отрыв >= 0.05.
  Слово «музей» само по себе не назначает историю. «Историческая кондитерская»
  не считается запросом исторического музея.
- Отрицания/исключения, несколько явно названных категорий и неподтверждаемые
  диеты/аллергены/другие распознаваемые условия требуют отдельного ввода. Результат
  содержит причину, предупреждения и `can_apply=false`; описания не возвращаются.
- При отсутствии контекста и уверенного профиля тема не применяется. Когда близкие
  описания есть, но категория неоднозначна, остаётся явный ручной выбор.
- Прямой расчёт через `semantic_query` также проверяет `can_apply`: отклонённая тема
  возвращает 422 до вызова OSRM. Обычный расчёт без темы работает по прежним правилам.
- Composer не берёт источники из снимка с явным `can_apply=false`. Старые снимки без
  этого поля продолжают читаться по прежним правилам; история не переписывается.

Сопоставление темы не подтверждает каждое свойство места. В частности, категория
«еда» не подтверждает диету, а сходство текста не является вероятностью.
Пользователь по-прежнему проверяет предложение и явно применяет его к участнику
или группе. Несколько интересов задаются отдельными поисками/ползунками.

Словарь условий конечный; произвольные синонимы, сложные отрицания и требования
не распознаются универсально. Проверка виз и ограничений маршрута остаётся отдельной.

## Проверка

Помимо регрессий API/планировщика и источников, добавлены проверки запрета ручного
обхода в UI. На сохранённых ответах прежней модели выполняется replay всех 40 случаев;
он не считается новым измерением эмбеддингов. Replay предлагает 31 верную категорию
из 32 положительных случаев, без неверных назначений. Запрос о музее Карму без
явного слова категории остаётся с уточнением, прежний эталон для него сохранён.

До реализации и живого измерения зафиксирован `data/evaluation/semantic-validation.json`:
20 новых положительных формулировок и 12 проверок условий/отрицаний/нескольких тем/
отсутствия сведений. Это авторский дополнительный набор, не независимый слепой тест.
Пустая relevance у policy-кейсов означает отсутствие допустимого автоматического
контекста для этой операции, а не отсутствие в мире подходящих мест.

Для новых случаев проверяются также `expected_policy` (`can_apply`, `reason`).
Ошибки транспорта, неверные назначения и ручные уточнения считаются отдельно.
Не требуется добиваться назначения категории для каждого текста ценой ошибок.

Живые прогоны из `backend`:

```powershell
.\.venv\Scripts\python.exe evaluate_rag.py --explanations --output ../docs/semantic-search-evaluation.json --samples ../.local/evaluations/semantic-search-samples.jsonl
.\.venv\Scripts\python.exe evaluate_rag.py --dataset ../data/evaluation/semantic-validation.json --output ../docs/semantic-search-validation.json --samples ../.local/evaluations/semantic-validation-samples.jsonl
```

Результаты сохраняются отдельно от первого baseline; эталоны не подстраиваются
по живым ответам дополнительного набора. RAGAS заново не вычисляется: здесь
проверяются правила применения темы, точные метки и допустимость маршрутов.

## Живые результаты

Оба окончательных отчёта завершены с `inputs_unchanged=true`; исходный набор из 40
запросов и новый набор из 32 не изменялись после фиксации. Эмбеддинги те же.

| Проверка | До изменения | После изменения |
| --- | --- | --- |
| Верное предложение категории на исходных положительных запросах | 9/32 | 31/32 |
| Уточнение на исходных положительных запросах | 23/32 | 1/32 |
| Неверное автоматическое назначение в исходном наборе | 0 | 0 |
| Контекст без подтверждения в исходных восьми случаях | 2/8 | 0/8 |

`semantic-search-evaluation.json`: четыре повторных сценария планирования допустимы,
4 LLM-объяснения прошли проверку обязательных фактов/точного текста, без fallback.
Precision@3 (0,4792), Recall@3 (0,9661) и nDCG@3 (0,9767) положительных запросов
остались прежними. Изменено применение темы, а не ранжирование этих документов.

`semantic-search-validation.json`: **16/20** положительных запросов получили верную
категорию, четыре остались с уточнением, неверных назначений нет. Все **12/12**
policy-кейсов прошли проверки `can_apply`/`reason`, контекст в них не возвращён.
Recall@3 — 0,9000, Precision@1 — 0,8000: на новых формулировках сам поиск тоже
ошибается. Дополнительный набор показывает границы, а не общую точность 100%.

Четыре неавтоматических случая:

- «Хочу разобраться в сопротивлении диктатуре» и «Хочу узнать о борьбе за гражданские
  свободы» — нет описания выше сохранённого порога; снижение порога по этим примерам
  не выполнялось.
- «Хочу увидеть произведения португальских мастеров» и пожелание утреннего набора
  из яиц/сока/йогурта — близкие описания есть, остаётся ручной выбор категории.

`semantic-policy-comparison.json` отдельно сравнивает старое правило профиля
на сохранённых округлённых scores нового прогона: 3/20 верных положительных
назначений и одно неуместное назначение для смешанного интереса (`new-29`).
Новое правило дало 16/20 и ноль таких назначений. Это **replay старого правила**,
не отдельный живой запуск старой версии. До границ решений более 0,0038,
поэтому округление до шести знаков не меняет эти решения.

Первый прогон дополнительных запросов прерван на записи отчёта из-за Windows
sharing violation. Его незавершённые снимки сохранены в игнорируемой `.local/`.
Добавлены пять ограниченных попыток атомарного replace при `PermissionError`;
предыдущий результат сохраняется, постоянная блокировка всё ещё вызывает ошибку.
Два теста проверяют временную и постоянную блокировку. Повторены только новые 32
запроса; правила поиска и эталоны в связи с этим сбоем не менялись.

После живых прогонов сужены границы двух словарных шаблонов: «искусственный интеллект»
не становится явным указанием искусства, «парковка» — парка. Добавлены два теста.
`semantic-policy-replay.json` подтверждает неизменность всех 72 сохранённых решений
после этого уточнения; это replay scores, а не новые вызовы модели. Источники
живых отчётов — коммиты `930d598` и `d5a4449`, дополнительные изменения отражены
отдельно, исходные хеши измерений не переписаны.

## Интерфейс и применение

В браузере проверены предложения природы и еды, предупреждение о веганском условии
с отсутствующей кнопкой применения и применение еды только второму участнику:
его вес изменился с 50% на 100%, вес первого остался 50%. Проверка не создавала
групп/поездок. Тестовое применение и вес после проверки убраны.

Неуверенный запрос по-прежнему допускает ручной выбор при наличии близких описаний.
Для запрещённого применения ручной select также отсутствует; простая подстановка
категории в UI не обходит ответ сервера. Старые ответы без нового сообщения получают
понятный текст, соответствующий наличию категории.

Финальная проверка: **490 backend-тестов** с PostgreSQL/Redis/Qdrant и опциональным
RAGAS-окружением, **13 frontend-тестов**, TypeScript и production-сборка Next.js,
Ruff и `alembic check` пройдены. Проверен реальный поиск через Next-прокси:
положительная тема применяется, диеты/отрицания/несколько тем возвращают
`can_apply=false` и пустые matches. `/health` и `/docs` доступны на 8001,
frontend обновлён на прежнем 3001. Новые зависимости, модели или порты не добавлялись.
