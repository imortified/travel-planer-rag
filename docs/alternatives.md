# Альтернативы и сравнение

Ветка `feature/route-alternatives` основана на `feature/lisbon-catalog` (2a6db46).
Для одного запроса сохраняется набор из 0–3 допустимых маршрутов. Один и тот же
состав мест с другим порядком, временем или распределением по дням считается
одним вариантом. Все маршруты используют один снимок исходных данных по каждой дате.

## Поиск

Первый кандидат строится выбранным greedy/beam. Далее алгоритм повторяет расчёт,
исключая блоки необязательных мест найденных маршрутов. Размер блока — четверть
числа посещений с округлением вверх, не больше числа необязательных мест.
Рассматриваются до шести циклических блоков в порядке ID на кандидат; очередь
и число расчётов ограничены (не более 13, включая исходный).

В новых расчётах допустимые кандидаты сортируются по общей F (objective-function.md).
Один контекст нормировки используется во всех попытках: временные запреты не меняют
границы полезности и бюджет. При равенстве F применяются общие правила разрешения ничьих.
Из них выбираются до трёх вариантов с попарным расстоянием Жаккара не менее 0.25:
`|A △ B| / |A ∪ B|`, где A/B — множества посещённых POI за всю поездку.
При нахождении трёх вариантов поиск завершается.

Основной вариант — первый по указанному порядку среди найденных. Это эвристика:
ни глобальная оптимальность, ни нахождение всех существующих вариантов не гарантируются.
Необязательные места могут отсутствовать в альтернативе; обязательные и исходные
запреты не меняются. Независимая финальная проверка использует исходный запрос,
посуточные часы/переезды и общий бюджет. Недопустимые кандидаты в options не попадают.

Если найдено меньше трёх вариантов, возвращается `fewer_distinct_options_found`.
Если допустимых вариантов нет, options пуст, `no_feasible_options_found`, а diagnostic
содержит неудачный исходный результат. Это не доказательство отсутствия решения.
Недоступность внешних данных возвращает 422/503, без записи частичного набора.

## Метрики

`comparison` каждого маршрута содержит:

- `visit_count` — число посещений;
- `participant_utility` — сумма весов категорий посещений для каждого участника;
- `mean_utility` — среднее этих сумм;
- `min_utility` — наименьшая сумма у участника;
- `utility_gap` — разница максимальной и минимальной суммы, меньше означает
  более равный баланс, но сама по себе эта величина не означает высокую полезность.

Стоимость — `result.total_cost`, в евроцентах на всю группу за весь период.
Полезность вычисляется по снимку предпочтений TripRequest и данным соответствующего дня.
Это условные баллы, не прогноз впечатлений. Старая satisfaction остаётся средним
интересом на одно посещение (0–1); она отличается от накопленной полезности.
`result.objective` дополнительно хранит F, вклады, коэффициенты, время переездов и
нормированное покрытие интересов. `utility_gap` в сырых баллах отличается от штрафа P.

## API и сохранение

Из backend применить `uv run alembic upgrade head` (миграция 0005), затем перезапустить
backend. Для frontend выполнить `npm.cmd run build` и перезапустить сервер либо использовать dev.

| Метод | Назначение |
| --- | --- |
| `POST /api/v1/trips/{id}/route-sets?algorithm=beam&beam_width=32` | Рассчитать и сохранить набор |
| `GET /api/v1/route-sets/{id}` | Открыть набор со всеми вариантами |
| `GET /api/v1/trips/{id}/route-sets` | История наборов запроса |

Параметры: algorithm=beam (по умолчанию) или greedy, beam_width=1..128.
Ответ: id, trip_request_id, algorithm, search_info, diagnostic, created_at, options.
В options — обычные RouteOutput с route_set_id и comparison. Набор и все варианты
сохраняются одной транзакцией. Повторный POST создаёт новый набор, старый не изменяет.
В БД: route_sets и nullable связь route_options.route_set_id; старые результаты
остаются отдельными и читаются прежними эндпоинтами. POST /routes по-прежнему считает
один маршрут, по умолчанию greedy. GET /routes также включает варианты новых наборов.

В интерфейсе расчёт создаёт набор, таблица показывает стоимость, число посещений,
полезность и баланс. Кнопка столбца переключает расписание и отчёт, а отличия по местам
можно раскрыть в таблице. Выбор столбца локален; при повторном открытии основным
показывается первый вариант. История открывает последний расчёт запроса, включая
пустой набор; для старых одиночных результатов сохраняется прежнее поведение.

## Проверки

Автотесты проверяют различие состава, детерминизм, расчёт метрик, неизменность
обязательных/запрещённых мест, недоступные переезды, общий бюджет, ежедневные данные,
отсутствие повторов, 0/1/3 варианта, отклонение ошибочного результата алгоритма,
сохранение/чтение набора, снимки предпочтений и отказ источника без частичной записи.

Сквозная проверка через интерфейс на Lisbon, 2026-10-23–25, два участника,
бюджет 100 EUR: основной вариант 9 мест за 78 EUR; альтернативы по 6 мест за 42 и 54 EUR.
Все три прошли проверку; проверено переключение расписания и повторное открытие
набора из истории. Числа относятся к этому снимку каталога и предпочтений.
