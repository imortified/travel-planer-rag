# Redis: TTL-кэш внешних API

Этап `feature/redis-api-cache` основан на `feature/qdrant-storage`.
Redis хранит временные ответы OSM и матрицы времени переезда OSRM. Векторы остаются
в Qdrant, а группы, запросы и неизменяемые снимки маршрутов — в PostgreSQL.
Новых миграций PostgreSQL для этого этапа нет.

## Запуск

Из корня проекта:

```powershell
docker compose up -d --wait redis
```

На другой машине синхронизировать обновлённые Python-зависимости и запустить backend:

```powershell
cd backend
uv sync --locked
.\.venv\Scripts\python.exe -m uvicorn app.main:app --host 127.0.0.1 --port 8001
```

Если backend уже работает без `--reload`, его нужно перезапустить.
Для семантического поиска также должны работать Qdrant и llama.cpp с эмбеддингами.

Используется официальный образ `redis:8.10.2-alpine`, закреплённый по SHA256.
Порт опубликован только на `127.0.0.1:6379`. Docker healthcheck выполняет `redis-cli ping`.
Кэш ограничен 128 MB с политикой `allkeys-lru`: при нехватке памяти записи могут быть
вытеснены раньше TTL. Redis работает без RDB/AOF и без постоянного volume; после
перезапуска кэш пустой и заполняется свежими ответами API. История поездок не теряется.

| Настройка `.env` | Значение по умолчанию |
| --- | --- |
| `REDIS_URL` | `redis://127.0.0.1:6379/0` |
| `REDIS_CACHE_PREFIX` | `travel:http:v1` |
| `REDIS_TIMEOUT_SECONDS` | `1` на подключение/команду |
| `OSM_CACHE_TTL_SECONDS` | `86400` — 24 часа |
| `OSRM_CACHE_TTL_SECONDS` | `3600` — один час |

При запуске backend в контейнере URL следует изменить на `redis://redis:6379/0`.
Поддерживается URL с учётными данными/TLS для другого Redis-сервера; секреты не входят
в Git или сообщения о сбое кэша. redis-py использует общий пул соединений; встроенные
повторные попытки отключены, чтобы отказ необязательного кэша не задерживал расчёт.

## Что сохраняется

- OSM: исходный XML выбранной области. Часы/пригодность мест вычисляются заново
  для запрошенной даты, затем применяются локальные проверенные дополнения каталога.
- OSRM: JSON ответа Table API, включая матрицу длительностей и сведения о точках.
  Округление секунд до минут и привязка строк к POI выполняются при каждом чтении.

Ключ имеет вид `travel:http:v1:osm:<sha256>` или `travel:http:v1:osrm:<sha256>`.
Отпечаток учитывает полный URL, параметры запроса и TTL. Для OSRM URL включает профиль
`driving` и **упорядоченные** координаты; другой порядок точек, профиль, источник или
параметры не переиспользуют неправильную матрицу. Ключ OSM не зависит от даты поездки:
кэшируется исходный XML, а недельное расписание интерпретируется отдельно для каждого дня.

Значение — JSON-конверт с версией, телом в base64, SHA256 тела и UTC-временем получения.
Запись значения и срока жизни выполняется одной командой `SET ... EX`.
Чтение не продлевает TTL и не заменяет время получения текущим временем.
Дополнительно проверяется возраст конверта: просроченная запись не используется,
даже если у её ключа ошибочно убрали Redis TTL. Будущие даты, повреждённые конверты,
контрольные суммы и неподходящие Redis-типы считаются невалидным кэшем.

Тело проверяется **до записи и после чтения**: XML должен быть корректным OSM,
матрица — иметь ожидаемые размеры и допустимые числовые длительности. `null` означает
недоступную связь и не подменяется выдуманным временем. Ошибки HTTP, некорректные XML,
отрицательные/нечисловые/булевы длительности не записываются.

Прежняя папка `data/.cache` больше не читается и не обновляется. Старые файлы оставлены
для совместимости с предыдущими ветками; автоматического импорта в Redis нет.

## Поведение при отказах

1. Свежий валидный кэш — использовать его без обращения к внешнему API.
2. Ключ отсутствует/истёк/повреждён — запросить свежие данные, проверить и сохранить.
3. Redis недоступен — запросить свежий внешний API, пропустить запись в Redis.
4. Redis отказал при записи — использовать уже проверенный свежий ответ.
5. Свежих данных нет и внешний API недоступен — вернуть 503. Просроченные файлы,
   старый Redis-конверт или синтетические POI не подставляются вместо реальных данных.

Сетевых попыток к внешнему источнику максимум две, с паузой 250 ms после первой
HTTP-ошибки; таймаут подключения 5 секунд, отдельной сетевой операции 40 секунд.
Некорректный успешный ответ отвергается сразу. Запросы к Redis не повторяются автоматически.
Блокировки на первое заполнение пока нет: параллельные холодные запросы могут
дублировать обращения к внешнему API. Записываются только проверенные ответы с TTL.

В API каталога и в `result.data_context.cache` маршрута сохраняются отдельные отчёты
`osm` и `osrm`: `backend`, непрозрачный `key`, `ttl_seconds`, `read` и `write`.

| Поле | Значения |
| --- | --- |
| `read` | `hit`, `miss`, `invalid`, `unavailable` |
| `write` | `stored`, `not_attempted` при hit, `skipped` после отказа чтения Redis, `unavailable` при отказе записи |

Отчёт описывает конкретный расчёт; в старых маршрутах он не меняется после истечения
TTL или остановки Redis. Даты `fetched_at` / `routing_fetched_at` относятся к получению
исходных ответов, а не к моменту чтения кэша. В старых результатах до этого этапа поля
`cache` может не быть.

## Проверка

```powershell
docker compose exec redis redis-cli --scan --pattern 'travel:http:v1:*'
# Подставить ключ из списка:
docker compose exec redis redis-cli TTL 'travel:http:v1:osm:<sha256>'

cd backend
$env:RUN_DB_TESTS='1'
$env:RUN_QDRANT_TESTS='1'
$env:RUN_REDIS_TESTS='1'
.\.venv\Scripts\python.exe -m pytest -q
```

Redis-тесты работают с уникальными `test:travel:*` ключами и удаляют только их;
`FLUSHDB`/`FLUSHALL` не используются. Проверяются реальное истечение TTL, повторная
загрузка, общий кэш для экземпляров backend, повреждённые записи, отсутствие продления
TTL, недоступность чтения/записи и отказ внешнего API.

В живом API проверены `miss → hit` для OSM и OSRM и реальные TTL через Redis. Расчёт
вернул три допустимых варианта, основной — 56 EUR для двух участников. При остановленном
Redis новый маршрут успешно рассчитан по свежим OSM/OSRM данным с `read=unavailable`,
а сохранённый маршрут остался доступен с прежним отчётом. Redis затем восстановлен.

Итоговая проверка этапа: 160 тестов с PostgreSQL, Qdrant и Redis, Ruff, alembic check
и проверка uv.lock прошли. Интерфейс и алгоритмическое ядро не изменялись.

Официальные источники: [SET с EX](https://redis.io/docs/latest/commands/set/),
[таймауты и повторы redis-py](https://redis.io/docs/latest/develop/clients/redis-py/produsage/),
[стабильные выпуски Redis](https://download.redis.io/releases/).
