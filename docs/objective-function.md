# Общая целевая функция маршрута

Ветка `feature/shared-objective` создана от `feature/visa-rules`.
Версия функции: `normalized-group-objective-v1`.
Для запросов с выбранным темпом добавлена версия v2 с бонусом заполнения дней D;
прежний режим и результаты экспериментов v1 сохранены. [Темп и формула v2](trip-pace.md).
Код: `backend/app/planning/objective.py`.

## Формула и область

Структура критерия из подраздела «Оптимизация маршрута» черновика записки
конкретизирована следующим образом:

```text
F(S) = α · R(S) − β · C(S) − γ · T(S) − λ · P(S)
α = 1; β = 0,15; γ = 0,15; λ = 0,35
```

Выше F — лучше. Коэффициенты являются исходной настройкой для экспериментов,
не эмпирически установленным оптимальным выбором. Они явно заданы в `Weights`,
сохраняются в каждом отчёте и доступны для изменения в офлайн-экспериментах.
Пользовательского редактирования коэффициентов в API/форме пока нет.
CP-SAT и начальное исследование чувствительности реализованы в следующем этапе:
[cp-sat.md](cp-sat.md). Калибровка на репрезентативных данных ещё требуется.

Сравниваются маршруты одного запроса с одинаковыми участниками, датами, бюджетом,
снимком кандидатов и коэффициентами. Оценка не является рейтингом поездки или
процентом удовлетворённости и не сопоставима напрямую между разными запросами.
Стоимость включает только входные билеты на всю группу.

Жёсткие ограничения сохраняются: бюджет, часы работы, длительность дня, достижимость,
обязательные/запрещённые POI, отсутствие повторов. Для выполнимости нужен хотя бы
один визит за весь период; отдельные пустые дни разрешены.
Нарушение не компенсируется большим F. Визовые риски остаются отдельным предупреждением.
У недопустимого результата публичное поле `objective=null`.

## Нормировка

Пусть A — объединение кандидатов всех дней без исходно запрещённых POI.
Каждое место учитывается в A один раз. В текущем каталоге у POI одна категория;
полезность для участника u на дате d равна весу этой категории `w[u, category(c,d)]`.
Это конкретизация категориальной награды; косинусное сходство из retrieval не подставляется
в неё как дополнительный множитель. Веса участников пока равны единице.

Для участника определим:

```text
Uu(S) = сумма весов категорий фактически посещённых мест на датах посещений
Hu = сумма по c ∈ A максимального веса категории c среди дат его доступности
su(S) = Uu(S) / Hu при Hu > 0; иначе 0
```

Hu — верхняя граница по каталогу, которая игнорирует бюджет, совместимость окон и
переезды. Она не является доказанным достижимым оптимумом. Максимум по датам нужен,
чтобы не считать один POI повторно и поддерживать дату-зависимые категории.

Четыре члена формулы:

| Член | Определение |
| --- | --- |
| R | Средняя накопленная полезность участников, делённая на среднее Hu; 0, если все Hu равны нулю |
| C | Суммарная стоимость билетов всей группы / общий бюджет B |
| T | Суммарное время переездов / `D × (end − start)` |
| P | `max(su) − min(su)` среди участников с Hu > 0; 0 при отсутствии таких участников |

Для допустимого маршрута члены находятся в [0,1] с учётом погрешности float.
При B=0 допустимы только бесплатные посещения, C=0; деления на ноль нет.
Участник с нулевым Hu сохраняется в группе и отчёте, но не участвует в штрафе P:
нет основания требовать покрытия отсутствующих в каталоге интересов. Такие ID явно
перечислены в `excluded_from_fairness`, а интерфейс предлагает уточнить предпочтения
или расширить каталог. Это не означает, что их интересы удовлетворены.

Время переездов включает путь от дневного старта до первого места и между местами.
На каждом дне исходная точка та же. Ожидание открытия, посещение, обратный путь и
междугородние переезды в T не входят. Время вычисляется по `arrival − previous.end`
(для первого визита — `arrival − request.start`); независимый валидатор проверяет
эти прибытия по сохранённой матрице. Билеты рассчитываются по фактической дате визита.

## Использование в алгоритмах

Один `Objective` создаётся на исходный запрос и общий набор дневных данных.
Этот контекст передаётся всем алгоритмам и попыткам построения альтернатив:

- **Greedy:** среди доступных продолжений выбирает лучшее по оценке полного
  текущего префикса. Обязательные посещения имеют приоритет. После выполнения
  обязательных мест прекращает добавления, которые не улучшают общий ключ.
- **Beam:** ранжирует частичные решения и выбирает результат по той же F;
  результат Greedy остаётся резервным кандидатом. Исследуются также продолжения,
  которые пока уступают лучшему результату: последующие визиты могут улучшить баланс.
- **Несколько дней:** оценка включает уже построенные дни. Знаменатели бюджета,
  времени и Hu остаются общими, а не пересчитываются по остатку бюджета или новому дню.
- **Альтернативы:** временные запреты меняют пространство поиска, но не A, Hu и
  бюджет нормировки. Готовые варианты проходят независимую проверку исходного запроса
  и сортируются по общей F. Разнообразие по Jaccard сохранено; Парето-отбора пока нет.

Поиск сначала предпочитает выполнение обязательных условий и их покрытие.
Среди допустимых решений сравнивается F, округлённая до 12 знаков для устойчивости
плавающей арифметики. Только при равенстве используются число непустых дней,
меньшая максимальная нагрузка дня, стоимость, переезды и стабильный порядок
дат/времени/ID. Эти правила разрешают ничьи и не заменяют взвешенную функцию.
Greedy остаётся локальной эвристикой, Beam ограничен шириной и не гарантирует оптимума.
Вставки в произвольную позицию готового дня пока нет: оба метода расширяют конец дня.

## Пример изменения поведения

Один участник, два места с одинаковыми окнами; успеть можно только в одно.
Интерес к искусству — 1, к истории — 0,9. Галерея стоит весь бюджет, историческое
место бесплатно; переезды нулевые, штраф P для одного участника нулевой.

```text
Галерея: F = 1 / 1,9 − 0,15 × 1 = 0,3763
История: F = 0,9 / 1,9            = 0,4737
```

Оба алгоритма выбирают историческое место. При β=0 выбирают галерею.
Для группы с интересами только history/nature платный рынок с нулевым интересом
больше не добавляется автоматически: он увеличивает расходы и не даёт награды.
Обязательный рынок всё равно должен быть включён или результат будет недопустимым.
Лимит 300 EUR не означает, что нужно потратить 300 EUR; малый каталог всё ещё
может исчерпать подходящие места намного раньше.

## Сохранение, интерфейс и совместимость

`Result.objective` содержит значение F, четыре вклада, коэффициенты, версию,
сырые полезности, покрытия, Hu, границу R, число кандидатов, исходный бюджет,
число доступных минут и время переездов. Отчёт хранится в JSON результата
PostgreSQL вместе с маршрутом, при чтении истории не пересчитывается.
Новая миграция БД не требуется. Старые результаты получают `objective=null`.

Новые идентификаторы алгоритмов: `greedy-v2`, `beam-v2:w32`,
`greedy-period-v2:w32`, `beam-period-v2:w32`, наборы — `diverse-v2:beam:w32`.
Ширина луча в примерах — 32. `search_info.objective_version` фиксирует критерий набора.

В таблице вариантов показаны F, переезды и разрыв нормированного покрытия.
Отдельно сохранены прежние сырые полезности и разрыв в баллах: они не равны P.
Блок «Оценка маршрута» показывает формулу, вклады и нормировку.
LLM-объяснение `grounded-explanation-v4-objective` обязано включить сохранённый факт
об оценке. Пропуск или изменение вызывает шаблон. Старые сохранённые объяснения
не переписываются; при обновлении для старого результата используется прежнее правило.

## Проверки

`tests/test_objective.py`: независимый числовой расчёт, обмен полезности на цену,
влияние времени переездов и fairness, нулевые бюджеты/профили, общая шкала альтернатив,
несколько дней, дата-зависимые данные, недопустимые коэффициенты и защита объяснений.
PostgreSQL-тесты проверяют сохранение коэффициентов/вкладов/шкал и повторное чтение.
Прежние проверки выполнимости и сравнение с полным перебором малого сценария сохранены.

`python compare_algorithms.py` пересчитывает прежние шесть контрольных сценариев
и сохраняет F, версию функции, полезность и время. Для недопустимых результатов
F и полезность в этом отчёте равны null. Этот набор не является новым крупным
дипломным экспериментом. Расширенный набор и CP-SAT описаны отдельно в cp-sat.md.

Итог этапа: 201 тест с PostgreSQL, Qdrant и Redis прошёл; Ruff, форматирование,
`alembic check`, `uv lock --check` и production-сборка Next.js прошли.
В браузере проверены расчёт, сравнение, раскрытие вкладов и повторное открытие.
Настоящая Qwen3-4B через llama.cpp вернула объяснение в режиме `llm` с проверенными
фактами новой оценки. Новая миграция или загрузка моделей для этого этапа не требуются.
