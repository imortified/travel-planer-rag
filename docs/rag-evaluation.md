# Оценка поиска и объяснений RAG

Ветка `feature/rag-quality-evaluation` основана на `fix/grounded-trip-parsing`.
Это отдельный инструмент экспериментов; API, интерфейс и параметры рабочего поиска
не меняются. В логировании добавлены имя файла эксперимента и подавление обычных
сообщений `httpx2`, как у `httpx`. Зависимости судьи находятся в необязательной группе `evaluation`.

## Зафиксированный набор

- `data/evaluation/rag-catalog.json`: снимок 13 пригодных POI опубликованной версии
  каталога 35 для 2026-10-27. Чтение PostgreSQL без новой загрузки OSM.
- `data/evaluation/rag-queries.json`: 40 авторских запросов, из них 32 с релевантными
  описаниями и 8 без подтверждающих сведений. Метки и запросы зафиксированы до поиска.
- Оценка 2 означает прямую текстовую поддержку, 1 — частичную/поддержку только названием,
  все неуказанные ID снимка имеют оценку 0. Reference составлен из размеченных описаний.
- Это авторская регрессионная разметка, которая требует проверки человеком.
  Она не является независимым экспертным корпусом или слепой пользовательской выборкой.
  Релевантность относится к имеющимся текстам, а не ко всем свойствам места в реальности.

Для 32 поддержанных запросов считаются macro Precision@1/3/5, Recall@1/3/5,
graded nDCG@1/3/5 и MRR@1/3/5. Precision делится на фиксированный k, recall —
на число релевантных документов снимка, nDCG использует gain `2^grade-1`.
Пустой эталон получает `null`, а не идеальный recall. Для восьми остальных запросов
отдельно считаются выдача контекста без доказательств и правильность отказа
автоматического назначения категории. Отрицание категории и фильтрация описаний —
разные проверки, успешное уточнение категории не означает отсутствия ложного контекста.

Поиск использует настоящие Qwen3-Embedding-0.6B Q8_0 и Qdrant, отдельные коллекции
с префиксом `travel_eval_rag_20261024`. Ранжирование и пороги приложения сохранены.
Дополнительно фиксируются top-3 описания после порога 0.40: это набор для оценки
извлечения, а не автоматически контекст объяснения маршрута.

## Фактический контекст объяснения

Флаг `--explanations` заранее выбирает четыре запроса — по одному на категорию,
а не по результатам измерений. Используются обычные отбор кандидатов, OSRM,
greedy, независимый валидатор и composer объяснений. Параметры эксперимента:
два синтетических участника с одинаковым подтверждённым интересом, бюджет 100 EUR,
день 09:00–18:00. Группы и поездки в PostgreSQL не создаются.

Каталог фиксирован; маршрутизация берётся через обычный Redis-кэш/OSRM. В отчёт
попадают полная выдача, снимок маршрута и матрицы, источник/время OSRM, факты,
реальный ответ LLM, repair и финальный режим `llm`/`template`. Объяснение получает
вычисленные факты и до двух описаний посещённых мест по обычным правилам приложения.
RAGAS оценивает именно этот сохранённый контекст. Он не подтверждает актуальность
цен, корректность источников или допустимость маршрута: для этого остаются свои проверки.

## Запуск поиска

Из `backend`, при работающих Qdrant (6333), embedding server (8082), а для объяснений
также chat server (8081), Redis и доступном OSRM:

```powershell
.\.venv\Scripts\python.exe evaluate_rag.py --explanations --output ../docs/rag-retrieval-evaluation.json --samples ../docs/rag-samples.jsonl
```

Обычный запуск без флага не вызывает чат-модель/OSRM. Скрипт сохраняет промежуточный
отчёт после каждого случая. Итог содержит SHA-256 кода/данных/lock-файла и проверку
`inputs_unchanged`. Ошибки транспорта отделены от низких оценок поиска. При изменении
корпуса/описаний нужна новая версия и новая оценка; прежний baseline сохраняется.

## RAGAS и выбор судьи

Подключён RAGAS **0.4.3** с collections API:

- `ContextPrecisionWithReference` и `ContextRecall` для выдачи поиска с reference;
- `Faithfulness` для утверждений объяснения по переданным фактам.

У случаев без эталона/контекста сохраняется причина пропуска. Исключения, таймауты,
NaN и выход за диапазон 0–1 обозначаются ошибкой измерения, не нулём и не успехом.
Средние объяснений считаются отдельно для LLM и шаблона. Общей цифры «качество RAG» нет.

`ContextPrecisionWithReference` в установленной версии считает average precision
по вердиктам LLM, а не обычный Precision@k. Например, при вердиктах `[1, 0, 0]`
его значение близко к 1, хотя Precision@3 равен 1/3. Поэтому метрика RAGAS и точная
оценка по ID не заменяют друг друга; нерелевантный хвост надо смотреть отдельно.

До оценки нужна модель-судья и калибровка на `data/evaluation/ragas-calibration.json`:
8 простых авторских примеров с верными, неверными и смешанными утверждениями.
Измеряется совпадение с ожидаемой долей подтверждённых утверждений с допуском 0.1.
Даже 8/8 не доказывает надёжность на сложном русском тексте; нужна ручная сверка.
Промпты RAGAS на английском, тексты примеров на русском; адаптация промптов не выполнялась.

Судья выбирается отдельно от Qwen3-4B, создающей объяснения. Поддерживаются llama.cpp
и OpenAI API; модель не выбирается и не скачивается автоматически. Ключ API читается
только из переменной процесса `RAGAS_JUDGE_API_KEY`, не записывается в отчёт/код.
Для OpenAI используйте конкретный доступный snapshot, чтобы возвращаемый model alias
совпадал с запрошенным. Бесплатные кредиты и доступность модели не предполагаются.
В API OpenAI не передаются специфичные для llama.cpp `chat_template_kwargs`.

Для этого этапа пользователь выбрал **Qwen3-8B Q4_K_M локально**, без оплаты API.
Веса и revision фиксируются в `data/judge-runtime.json`, загрузка проверяет SHA-256.
Запуск: `scripts/start-ragas-judge.ps1`, порт 8083, контекст 8192, по умолчанию CPU,
чтобы не занимать видеопамять работающей Qwen3-4B. Порт 8081 остаётся у генератора,
8082 — у эмбеддингов. Отдельная модель того же семейства не устраняет общий bias.

Проверен и отклонён вариант GitHub Models: по [официальной документации GitHub](https://docs.github.com/en/github-models)
сервис полностью закрыт 2026-07-30. OpenAI API в этом этапе не вызывается;
его конфигурация проверена только контролируемыми тестами.

Изолированная установка (из `backend`):

```powershell
$env:UV_PROJECT_ENVIRONMENT='../.local/ragas-venv'
..\.venv\Scripts\uv.exe sync --group evaluation --locked
Remove-Item Env:UV_PROJECT_ENVIRONMENT
```

Зафиксирована совместимая `langchain-community<0.4`: версия 0.4.2 удаляет импорт,
который требуется RAGAS 0.4.3. Зависимости не устанавливаются в рабочий venv автоматически.

Пример для **отдельно установленного и согласованного** локального судьи:

```powershell
..\.local\ragas-venv\Scripts\python.exe score_ragas.py --calibration --samples ../data/evaluation/ragas-calibration.json --output ../.local/evaluations/ragas-calibration.json --backend llama-cpp --base-url http://127.0.0.1:8083/v1 --model Qwen3-8B-Q4_K_M --judge-identity 'указать revision и SHA256 весов'
..\.local\ragas-venv\Scripts\python.exe score_ragas.py --samples ../docs/rag-samples.jsonl --output ../.local/evaluations/ragas-scores.json --backend llama-cpp --base-url http://127.0.0.1:8083/v1 --model Qwen3-8B-Q4_K_M --judge-identity 'указать revision и SHA256 весов'
```

Для OpenAI заменяются `--backend openai`, URL на `https://api.openai.com/v1`, модель
и её identity. До платного прогона согласуются модель и расход. Можно ограничить
поднабор повторяемым `--case-id`. Для той же модели, что генерирует ответ, требуется
явный `--allow-self-judge`, результат остаётся самооценкой.

RAGAS работает последовательно, по умолчанию ограничивает HTTP-вызов 360 с,
одну метрику 720 с (в ней может быть несколько вызовов), сохраняет
сырые ответы и usage судьи, хеш промпта, версии библиотек, запрошенную/возвращённую
модель. API alias не является проверкой checksum весов локального сервера; для этого
в `judge-identity` отдельно фиксируется проверенная версия. Telemetry RAGAS отключена.

## Что уже проверено

Аналитические метрики проверены на вручную вычисленных примерах, включая короткую
выдачу, пустой эталон, дубли и перестановку graded relevance. Отдельные тесты используют
настоящие RAGAS/Instructor и контролируемый HTTP API для обеих конфигураций.
Они проверяют интеграцию и формулы библиотеки, а не качество модели-судьи.

## Первый живой результат поиска

Отчёт `rag-retrieval-evaluation.json`, samples `rag-samples.jsonl`, код коммита
`02849eb`. Все 40 поисков и четыре объяснения завершены, `inputs_unchanged=true`.
Ни модель, ни пороги не подстраивались по полученным оценкам.

| Метрика, 32 запроса с релевантными документами | Значение |
| --- | --- |
| Precision@1 / MRR@3 | 1,000 / 1,000 |
| Precision@3 / Recall@3 | 0,4792 / 0,9661 |
| nDCG@3 | 0,9767 |
| Precision@5 / Recall@5 | 0,3000 / 0,9818 |
| Recall в top-3 после порога 0.40 | 0,9115 |

У многих запросов только один релевантный документ, поэтому даже идеальный top-1
означает Precision@3 = 1/3 при двух лишних результатах. Высокий MRR не означает,
что все три описания полезны. Всего 13 кандидатов и авторские запросы с лексикой
описаний делают задачу небольшой; переносимость на большой каталог не измерена.

Из восьми запросов без подтверждающих сведений контекст после порога вернулся в двух:
вопрос о подтверждённом веганском бранче и отрицание исторических музеев. Категория
во всех восьми оставлена неизвестной. Это диагностирует выдачу неподтверждающего
контекста, а не доказывает, что маршрут нарушил запрет или что блюдо выдано за веганское.
В 32 положительных случаях категория назначена верно только в 9, остальные 23 —
уточнение, ошибочных автоматических назначений нет. Следовательно, поиск документов
и автоматическое подтверждение категории имеют разное покрытие.

Медиана поиска — 0,772 с, p95 — 1,017 с; начальная индексация входит в первый вызов
(максимум 4,442 с). В фоне загружались веса судьи, аппаратная нагрузка не контролировалась;
это не отдельный нагрузочный эксперимент и не измерение полного пользовательского пути.

Четыре маршрута допустимы, объяснения — 4 LLM / 0 template, без repair.
Каждое содержит одно извлечённое описание посещённого места, обязательные факты
и точные копии предложений. Время полного capture — 26,7–30,2 с. В PostgreSQL
новые поездки не создавались. У текущего composer свободное перефразирование
запрещено: будущий высокий Faithfulness в такой архитектуре не докажет качество
свободной генерации или полноту ответа, полнота проверяется отдельно.

Проверки перед прогоном: 427 backend-тестов с PostgreSQL/Redis/Qdrant в evaluation-venv;
после добавления метаданных судьи отдельно повторены 18 тестов оценки. Ruff,
форматирование и `alembic check` пройдены.

## Калибровка локального судьи

`ragas-judge-calibration.json`: **8/8** совпадений с заданными эталонами,
16 HTTP-генераций без ошибок. Подтверждённые утверждения получили 1, противоречащие
контексту — 0, смешанные — 0,5. Среднее 0,5 по контролям отражает состав примеров,
а не качество приложения. Набор маленький и авторский; это проверка работоспособности
судьи, которая не заменяет независимую ручную оценку сложных примеров.

Весовой файл Qwen3-8B Q4_K_M загружен и проверен по SHA-256 из manifest.
Калибровка выполнялась с контекстом 8192 и 18 слоями GPU на RTX 3050 4 GB;
на это время генератор 4B на 8081 был остановлен для освобождения VRAM. После оценки
генератор восстановлен, судья запущен на CPU на 8083. Пример запуска по умолчанию оставляет судью на CPU;
результаты времени GPU-прогона к CPU-режиму не переносятся.

Калибровка использовала HTTP timeout 90 с / metric timeout 180 с. Перед длинными
объяснениями добавлены параметры `--http-timeout` / `--metric-timeout` с большими
значениями по умолчанию; промпты, модель, эталоны и параметры генерации не менялись.
Повторно пройдены 18 тестов оценки. RAGAS-оценки основного набора сохраняются отдельно.

### Ограничение судьи, обнаруженное вне простых контролей

В `rag-03` («древние цивилизации и археология») описание Карму размечено релевантным
и совпадает с частью reference. Судья сам пишет, что описание соответствует вопросу,
но выдаёт `verdict=0`, потому что reference скопирован из контекста и не содержит
рассуждения. Это не требование Context Precision: копирование источника не делает
его нерелевантным. Здесь есть явный пример ошибки судьи; 8/8 простых контролей
не подтвердили его надёжность на всём наборе.

Поэтому значения RAGAS рассматриваются как дополнительная экспериментальная
оценка, требующая ручного аудита. Среднее не доказывает корректность каждого случая.
Для дальнейшей калибровки нужны независимо проверенные сложные примеры; текущие
промпты/эталоны не подстраиваются по увиденным результатам ради улучшения среднего.

Обычное backend-окружение без группы RAGAS отдельно проверено: 423 теста прошли,
четыре теста самого опционального адаптера пропущены. Это подтверждает отсутствие
обязательного runtime-импорта RAGAS у backend.

После изменения значений timeout и форматирования финально пройдены все **427**
тестов в evaluation-venv с PostgreSQL/Redis/Qdrant, Ruff, форматирование (включая
загрузчик весов) и `alembic check`. Проверены HTTP 200: frontend 3001, backend
8001 `/health` и `/docs`, модели 8081/8082/8083. Восстановленная Qwen3-4B на 8081
проверена короткой реальной генерацией. Судья на 8083 оставлен на CPU, его GPU-прогон
завершён. Миграции БД и изменение настроек основного генератора не требовались.

Хеши `input_sha256` фиксируют фактические байты файлов при измерении в Windows.
Git нормализует текстовые CRLF в LF, поэтому при сверке клонов нужно учитывать
переводы строк; это не изменение JSON-данных. В частности, исходный SHA256 samples
соответствует CRLF-файлу. Отчёты прошлых запусков ради нормализации не переписываются.
