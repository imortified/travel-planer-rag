## Быстрый запуск в PowerShell

Для уже настроенной рабочей копии достаточно одной команды из корня проекта:

```powershell
.\run.ps1
```

Предварительно запусти Docker Desktop. Скрипт поднимает PostgreSQL, Redis и Qdrant,
применяет миграции, запускает обе модели llama.cpp, backend на **8001** и интерфейс
на **3001**. Открыть http://127.0.0.1:3001; документация API —
http://127.0.0.1:8001/docs, проверка процесса — http://127.0.0.1:8001/health.
Все процессы работают под управлением одного терминала; **Ctrl+C** останавливает
запущенные им процессы. Docker-контейнеры и ранее запущенные подходящие процессы остаются
работать; контейнеры можно остановить отдельно: `docker compose stop`.
Работающие экземпляры приложения и нужных моделей используются повторно;
если порт занят другим приложением, запуск останавливается с сообщением.
При повторном использовании backend миграции пропускаются. После обновления кода
останови прежний backend и запусти скрипт снова, чтобы применить миграции.

Вывод каждого процесса сохраняется отдельно в `.local/logs/run-<дата-время>/`.
Скрипт сообщает путь к логам при ошибке запуска. Он не скачивает модели и зависимости,
не обновляет каталог и не запускает модель судьи RAGAS.

Дополнительные режимы:

```powershell
.\run.ps1 -CheckOnly       # Проверить окружение без запуска и миграций
.\run.ps1 -WithoutModels   # Запустить приложение без запуска локальных моделей
```

`-WithoutModels` оставляет доступной обычную форму; нейросетевые функции требуют
работающих серверов моделей. Используются стандартные локальные порты **8081/8082**
и текущие настройки `.env`. Ожидание каждого процесса — до 300 секунд,
его можно изменить параметром `-StartupTimeoutSeconds`.
Существующие контейнеры сохраняют свою конфигурацию (`--no-recreate`). Если Windows
запрещает привязку PostgreSQL к **55432**, выбери свободный порт, например **15432**:
измени `POSTGRES_PORT` и порт в `DATABASE_URL` в `.env`, затем выполни
`docker compose up -d --wait postgres` и перезапусти backend. Volume с данными сохраняется.
Если политика PowerShell запрещает запуск скрипта:
`powershell -NoProfile -ExecutionPolicy Bypass -File .\run.ps1`.

Первоначальная установка на новом компьютере:

Требуются Python 3.12 или 3.13, uv и Docker Desktop с Linux containers.
В текущей рабочей копии uv установлен в корневую `.venv`, а зависимости приложения —
в `backend/.venv`. На новом компьютере можно установить uv командой `python -m pip install uv`.

Из корня проекта:

```powershell
Copy-Item .env.example .env
docker compose up -d --wait
cd backend
uv sync --locked
uv run alembic upgrade head
uv run python refresh_catalog.py
uv run python -m app.run --reload
```

Если uv не находится в PATH, в этой рабочей копии вместо `uv` используй
`..\.venv\Scripts\uv.exe` из папки `backend`.

API: http://127.0.0.1:8001/docs. Проверка процесса: http://127.0.0.1:8001/health.
`refresh_catalog.py` требует доступа к OSM; последующие чтения каталога берут опубликованную
версию из БД. Новый расчёт также требует матрицу OSRM из Redis или внешнего API.
`/health` не проверяет подключение к БД. Для запуска демонстрационного расчёта БД не нужна.
Переменные приложения читаются из `.env` в корне независимо от рабочей папки.
Пароль из примера предназначен только для локальной разработки.

Пример из второго терминала:

```powershell
$payload = @{
    participants = @(
        @{ id = 'alice'; interests = @{ history = 1.0; food = 0.5 } }
        @{ id = 'bob'; interests = @{ nature = 1.0; food = 0.8 } }
    )
    budget = 10000
    start = 540
    end = 1080
    mandatory = @('museum')
    excluded = @()
} | ConvertTo-Json -Depth 5
Invoke-RestMethod -Method Post -Uri http://127.0.0.1:8001/api/v1/plans/demo -ContentType 'application/json' -Body $payload
```

## Группы и сохранённые поездки

После обновления кода применить миграции: `uv run alembic upgrade head` из `backend`.
Перезапустить backend, если он запущен без `--reload`.

| Метод и путь | Назначение |
| --- | --- |
| `POST /api/v1/users` | Создать участника: `{"name":"Alice"}` |
| `GET /api/v1/users/{id}` | Получить участника |
| `POST /api/v1/groups` | Создать группу: `{"name":"Friends"}` |
| `GET /api/v1/groups/{id}` | Группа с участниками и предпочтениями |
| `POST /api/v1/groups/{id}/members` | Добавить участника: `{"user_id":1}` |
| `PUT /api/v1/groups/{id}/members/{user_id}/preferences` | Заменить предпочтения: `{"interests":{"history":1}}` |
| `POST /api/v1/groups/{id}/trips` | Сохранить запрос: `{"budget":10000}` |
| `GET /api/v1/groups/{id}/trips` | Список запросов группы |
| `GET /api/v1/trips/{id}` | Запрос со снимком участников и предпочтений |
| `POST /api/v1/trips/{id}/routes` | Рассчитать и сохранить новый результат |
| `GET /api/v1/trips/{id}/routes` | Список результатов расчёта |
| `GET /api/v1/routes/{id}` | Прочитать сохранённый результат |
| `POST /api/v1/trips/{id}/route-sets` | Рассчитать и сохранить до трёх разных допустимых вариантов |
| `GET /api/v1/route-sets/{id}` | Прочитать набор со сравнением |
| `GET /api/v1/trips/{id}/route-sets` | История наборов вариантов |

Предпочтения хранятся в участии пользователя в конкретной группе.
Группа содержит не более шести участников. Добавление повторного участника,
седьмого участника или поездки для пустой группы возвращает 409.
Неверный ввод возвращает 422, отсутствующие сущности — 404.

Запрос поездки сохраняет состав группы и предпочтения на момент создания.
Изменения профилей не меняют старые запросы; для новых предпочтений создаётся новый запрос.
Каждый POST расчёта создаёт отдельную запись с версией алгоритма и источником данных.
Сохраняются и неудачные результаты с `is_feasible=false` и причинами.
Доступны синтетический Demo City и реальные данные Lisbon, суммы в EUR.

Каждый новый расчёт проходит независимую проверку `planning/validator.py`.
В `result.validation` возвращаются `is_valid`, пересчитанная стоимость `computed_cost`
и список `violations` с кодом, описанием, ID места и индексом посещения (с нуля).
Проверяются бюджет, стоимость, временной порядок, границы дня, часы работы,
минимальная длительность, достижимость, наличие данных переезда, обязательные,
запрещённые, неизвестные и повторные места. Ожидание открытия и дополнительные
паузы разрешены. Маршрут без посещений считается невыполнимым.
Ошибка проверки снимает `is_feasible`, даже если алгоритм заявил успех.
Причины ошибки добавляются в `reasons`; подробности доступны в отчёте.
Для ранее сохранённых результатов без отчёта `validation` возвращается как `null`;
новый отчёт можно получить новым расчётом поездки. Миграция БД не требуется.

Пример успешного отчёта:

```json
{"is_valid": true, "computed_cost": 5400, "violations": []}
```

Проверка использует переданный набор POI и матрицу переездов. Она не подтверждает
актуальность исходных данных, визы, погоду или обратный путь к месту проживания.

Полный пример из корня проекта при запущенном API:

```powershell
.\scripts\demo-group.ps1
```

Скрипт создаёт новую демонстрационную группу, двух пользователей, запрос и результат
в рабочей БД. API этой итерации предназначен для локальной разработки;
вход обязателен, группы и история изолированы по владельцу. Скрипт запрашивает почту и пароль.
Аккаунты, сохранённые участники и перенос прежних поездок: [docs/accounts.md](docs/accounts.md).

Последняя команда проверяет генерацию SQL без БД; реальное применение миграции
выполняется отдельной командой `uv run alembic upgrade head` после запуска PostgreSQL.
`uv.lock` фиксирует разрешённые версии зависимостей; коммитить его вместе с pyproject.toml.

## Структура

- `backend/app/api`, `schemas` — HTTP и валидация входных данных.
- `backend/app/planning` — чистый Python: модели и расчёт маршрута.
- `backend/app/integrations` — загрузка демонстрационных данных, затем адаптеры внешних API.
- `backend/app/db`, `alembic` — модели и миграции; первая миграция создаёт users и PostGIS.
- `data/demo.json` — синтетические POI и направленная матрица времени переездов.
- `docs/mvp.md` — правила и этапы реализации.
- `frontend` — Next.js + TypeScript: группы, предпочтения, поездки и результаты расчёта.

## Текущее поведение

Добавлен [поиск и выбор проживания](docs/lodging.md): каталоги PostgreSQL для трёх
городов, фильтры названия/адреса/типа, сайты из OSM, заезд/выезд/номера и сохранённый
выбор с возрастами. Миграция `0013`. Ручной каталог дополнен
[ценами Xotelo](docs/xotelo-lodging.md), миграция `0014`: даты и состав группы,
TTL-кэш Redis, явный перенос базовой оценки одного номера и сохранение источника.
Итоговая цена с налогами, наличие, вместимость, детские условия и бронирование
не подтверждаются. Для нескольких номеров нужна ручная общая оценка.

Подготовлен отдельный [пилот Xotelo и SerpApi](docs/hotel-provider-comparison.md).
Xotelo проверен на 12 сценариях; живое сравнение с SerpApi требует локального ключа
его бесплатного аккаунта. Пилот не изменяет цены в бюджете и не оформляет бронирования.

Проверен [доступ к Aviasales Data API](docs/aviasales-data-access.md): пять живых
сценариев, токен только в локальном `.env`, команда `backend/check_aviasales.py`.
На основе пилота добавлены [поиск и сохранение перелётов](docs/flights.md):
карточки в интерфейсе, ссылки на перепроверку, Redis TTL и история PostgreSQL,
миграция `0015`. Общая сумма авиабилетов для группы вводится отдельно от наземного
транспорта. Цены из кэша справочные; покупка и автоматическая коррекция расписания
по времени прилёта не выполняются.

Добавлены [возраст участников и индивидуальные тарифы](docs/age-pricing.md):
возраст на начало поездки либо дата рождения, проверенные возрастные билеты у 9 мест,
сумма по участникам во всех алгоритмах и замороженная история. Нужна миграция `0012`.
При непроверенной льготе применяется обычный тариф с пояснением.
Питание пока использует одинаковый выбранный заказ для детей и взрослых.

Добавлены [питание в расписании и разбивка бюджета](docs/meals-budget.md):
завтрак/обед/ужин по выбранным окнам, конкретные проверенные заказы, отдельные
оценки жилья/транспорта и резерв. При включённом режиме полного бюджета эти
оценки вычитаются до расчёта остановок. Неуказанные суммы помечаются отдельно;
бронирование и цены проживания/перелётов не подтверждаются. Для новых полей
нужна миграция `0011`. Без этих настроек действует прежний бюджет остановок.

Расчёт выполняется на 1–14 дней в Demo City, Lisbon, Porto или Sintra.
Один город и его окрестности на поездку; каждый день начинается в точке `start`.
Время — минуты от полуночи по местному времени, суммы — целые евроценты.
Бюджет общий для группы; стоимость посещения равна сумме индивидуальных билетов.
При отсутствии подтверждённой возрастной льготы действует обычный тариф.
Учитываются ожидание открытия, длительность посещения и переезды. Возвращение
к месту проживания пока не моделируется. В результат включаются только посещения,
помещающиеся в бюджет и временные окна.

Обязательные POI имеют приоритет. Далее сравнивается общая нормированная оценка
интересов, стоимости, переездов и баланса (objective-function.md).
Запрет относится к группе целиком. Конфликт запрета и обязательного POI возвращается явно.
При недостающем времени переезда переход считается недоступным.
Незапланированные обязательные POI делают результат `is_feasible=false`.
Неуспех greedy или ограниченного beam search не доказывает отсутствие допустимого маршрута.
Частичный маршрут при неуспехе возвращается только для диагностики.

Удовлетворённость — средний интерес участника к категориям посещённых POI,
число от 0 до 1; это начальная метрика, а не полная fairness-оптимизация.
Визовые требования и сроки проверяются по ограниченному справочнику; действительность
документов и право въезда не подтверждаются. Погода и авторизация пока не реализованы.
Начальный семантический поиск
и RAG с проверяемыми описаниями доступны в отдельном блоке интересов; корпус небольшой.

## Выбор алгоритма

У эндпоинтов расчёта есть query-параметры `algorithm=greedy|beam` и
`beam_width=1..128` (по умолчанию 32). Одиночный /routes по умолчанию использует
прежний greedy, а новый /route-sets — beam.
Пример расчёта для уже сохранённого запроса поездки:

```powershell
Invoke-RestMethod -Method Post -Uri 'http://127.0.0.1:8001/api/v1/trips/3/routes?algorithm=beam&beam_width=32'
```

Полный новый сценарий:

```powershell
.\scripts\demo-group.ps1 -BaseUrl http://127.0.0.1:8001 -Algorithm beam
```

В новых расчётах сохраняется `algorithm=beam-v2:w32`. Оба алгоритма проходят один независимый валидатор.
Beam search ограничивает число рассматриваемых состояний на каждом шаге шириной луча;
результат greedy также участвует в выборе, поэтому результат не хуже него по принятому
порядку оценки. Это эвристика без гарантии глобального оптимума или нахождения любого
существующего допустимого маршрута. Ограничение текущей реализации — 100 кандидатов POI.

Порядок выбора: выполнимость и покрытие обязательных мест → общая оценка F;
при равенстве — распределение по дням, стоимость, переезды и стабильный порядок.
`F = R − 0,15C − 0,15T − 0,35P`: нормированные интересы, стоимость, переезды,
разрыв покрытия интересов. Определения и начальные коэффициенты —
[docs/objective-function.md](docs/objective-function.md). Старые результаты не пересчитываются.
Сырые суммы интересов и `satisfaction` сохранены отдельно; Парето-отбор ещё не реализован.

Сравнение без БД из `backend`:

```powershell
.\.venv\Scripts\python.exe compare_algorithms.py
```

Методика и выводы: [docs/algorithm-comparison.md](docs/algorithm-comparison.md).
Машинный отчёт: `docs/algorithm-comparison.json`.

## Реальные POI: Лиссабон

Расширенный этап поддерживает **Лиссабон, Порту и Синтру**: загрузку из PBF
Португалии, отдельные версии в PostgreSQL и поиск в Qdrant. В каталогах
913/513/206 записей, но в расчёт включаются только объекты с известными ценами,
часами и доступом. На 26 октября — 1 ноября доступны 45/25/12 различных мест.
Добавлен справочник 764 населённых пунктов; планирование пока поддерживает три
направления. Источники, команды загрузки и проверка —
[docs/portugal-catalogs.md](docs/portugal-catalogs.md).
Ниже сохранён первоначальный способ загрузки малого района Лиссабона.

Для реального каталога нужна миграция `0009` и опубликованная версия. Из `backend`:

```powershell
uv sync --locked
uv run alembic upgrade head
uv run python refresh_catalog.py
```

При запущенном API полный сценарий из корня:

```powershell
.\scripts\demo-group.ps1 -BaseUrl http://127.0.0.1:8001 -Algorithm beam -Destination Lisbon -TravelDate 2026-10-23
```

`GET /api/v1/destinations` показывает доступные направления.
`GET /api/v1/destinations/Lisbon/pois?travel_date=2026-10-23` возвращает каталог с именами,
координатами, источниками, расписанием и причинами исключения. Для сохранённого запроса
используй `destination=Lisbon` и `travel_date=YYYY-MM-DD`; прочие эндпоинты не меняются.

Дата нужна для проверки недельного расписания и исключений. При расчёте сохраняются
источники, время получения, имена, координаты POI, нормализованные окна и матрица
переездов в `result.data_context`. Новые результаты имеют `data_source=osm-osrm-lisbon-v2`.

Подробности и ограничения: [docs/real-data.md](docs/real-data.md).

## Инфраструктура

Данные БД сохраняются в Docker volume. Остановка без удаления данных:
`docker compose down`. Backend пока запускается локально для удобства разработки.
PostgreSQL доступен по `127.0.0.1:55432`, внутри контейнера используется порт 5432.
Qdrant доступен по `127.0.0.1:6333`, данные сохраняются в отдельном `qdrant_data` volume.
Запуск только векторного хранилища: `docker compose up -d --wait qdrant`.
Redis доступен по `127.0.0.1:6379`: OSM кэшируется на 24 часа, матрицы OSRM — на час.
Запуск: `docker compose up -d --wait redis`; кэш временный, без постоянного volume.
Celery, nginx и контейнер backend пока не добавлены.
