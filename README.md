# Групповое планирование путешествий

Backend для дипломного проекта: FastAPI, PostgreSQL/PostGIS, Alembic,
greedy и beam search с независимой валидацией. Доступны синтетический Demo City
и реальные POI центра Лиссабона через OpenStreetMap с автомобильными переездами OSRM.

## Веб-интерфейс

Из `frontend` запустить `npm.cmd ci`, затем `npm.cmd run dev` и открыть
http://127.0.0.1:3000. Backend должен работать на порту 8001.
Можно создавать и загружать группы, задавать интересы, строить маршруты и читать
сохранённые результаты. Инструкция: [frontend/README.md](frontend/README.md).

## Быстрый запуск в PowerShell

Требуются Python 3.12 или 3.13, uv и Docker Desktop с Linux containers.
В текущей рабочей копии uv установлен в корневую `.venv`, а зависимости приложения —
в `backend/.venv`. На новом компьютере можно установить uv командой `python -m pip install uv`.

Из корня проекта:

```powershell
Copy-Item .env.example .env
docker compose up -d --wait
cd backend
uv sync --locked
uv run alembic upgrade head
uv run uvicorn app.main:app --reload
```

Если uv не находится в PATH, в этой рабочей копии вместо `uv` используй
`..\.venv\Scripts\uv.exe` из папки `backend`.

API: http://127.0.0.1:8000/docs. Проверка процесса: http://127.0.0.1:8000/health.
`/health` не проверяет подключение к БД. Для запуска демонстрационного расчёта БД не нужна.
Переменные приложения читаются из `.env` в корне независимо от рабочей папки.
Пароль из примера предназначен только для локальной разработки.

Пример из второго терминала:

```powershell
$payload = @{
    participants = @(
        @{ id = 'alice'; interests = @{ history = 1.0; food = 0.5 } }
        @{ id = 'bob'; interests = @{ nature = 1.0; food = 0.8 } }
    )
    budget = 10000
    start = 540
    end = 1080
    mandatory = @('museum')
    excluded = @()
} | ConvertTo-Json -Depth 5
Invoke-RestMethod -Method Post -Uri http://127.0.0.1:8000/api/v1/plans/demo -ContentType 'application/json' -Body $payload
```

## Проверки

Из `backend`:

```powershell
uv run pytest
uv run ruff check .
uv run ruff format --check .
uv run alembic upgrade head --sql
```

Интеграционные тесты используют настоящий PostgreSQL с применёнными миграциями.
Каждый тест работает в транзакции и откатывает свои записи:

```powershell
$env:RUN_DB_TESTS = '1'
uv run pytest
Remove-Item Env:RUN_DB_TESTS
```

## Группы и сохранённые поездки

После обновления кода применить миграции: `uv run alembic upgrade head` из `backend`.
Перезапустить backend, если он запущен без `--reload`.

| Метод и путь | Назначение |
| --- | --- |
| `POST /api/v1/users` | Создать участника: `{"name":"Alice"}` |
| `GET /api/v1/users/{id}` | Получить участника |
| `POST /api/v1/groups` | Создать группу: `{"name":"Friends"}` |
| `GET /api/v1/groups/{id}` | Группа с участниками и предпочтениями |
| `POST /api/v1/groups/{id}/members` | Добавить участника: `{"user_id":1}` |
| `PUT /api/v1/groups/{id}/members/{user_id}/preferences` | Заменить предпочтения: `{"interests":{"history":1}}` |
| `POST /api/v1/groups/{id}/trips` | Сохранить запрос: `{"budget":10000}` |
| `GET /api/v1/groups/{id}/trips` | Список запросов группы |
| `GET /api/v1/trips/{id}` | Запрос со снимком участников и предпочтений |
| `POST /api/v1/trips/{id}/routes` | Рассчитать и сохранить новый результат |
| `GET /api/v1/trips/{id}/routes` | Список результатов расчёта |
| `GET /api/v1/routes/{id}` | Прочитать сохранённый результат |

Предпочтения хранятся в участии пользователя в конкретной группе.
Группа содержит не более шести участников. Добавление повторного участника,
седьмого участника или поездки для пустой группы возвращает 409.
Неверный ввод возвращает 422, отсутствующие сущности — 404.

Запрос поездки сохраняет состав группы и предпочтения на момент создания.
Изменения профилей не меняют старые запросы; для новых предпочтений создаётся новый запрос.
Каждый POST расчёта создаёт отдельную запись с версией алгоритма и источником данных.
Сохраняются и неудачные результаты с `is_feasible=false` и причинами.
Маршрут пока рассчитывается по синтетическим данным Demo City в EUR.

Каждый новый расчёт проходит независимую проверку `planning/validator.py`.
В `result.validation` возвращаются `is_valid`, пересчитанная стоимость `computed_cost`
и список `violations` с кодом, описанием, ID места и индексом посещения (с нуля).
Проверяются бюджет, стоимость, временной порядок, границы дня, часы работы,
минимальная длительность, достижимость, наличие данных переезда, обязательные,
запрещённые, неизвестные и повторные места. Ожидание открытия и дополнительные
паузы разрешены. Маршрут без посещений считается невыполнимым.
Ошибка проверки снимает `is_feasible`, даже если алгоритм заявил успех.
Причины ошибки добавляются в `reasons`; подробности доступны в отчёте.
Для ранее сохранённых результатов без отчёта `validation` возвращается как `null`;
новый отчёт можно получить новым расчётом поездки. Миграция БД не требуется.

Пример успешного отчёта:

```json
{"is_valid": true, "computed_cost": 5400, "violations": []}
```

Проверка использует переданный набор POI и матрицу переездов. Она не подтверждает
актуальность исходных данных, визы, погоду или обратный путь к месту проживания.

Полный пример из корня проекта при запущенном API:

```powershell
.\scripts\demo-group.ps1
```

Скрипт создаёт новую демонстрационную группу, двух пользователей, запрос и результат
в рабочей БД. API этой итерации предназначен для локальной разработки;
аутентификация и проверка доступа к группам пока не реализованы.

Последняя команда проверяет генерацию SQL без БД; реальное применение миграции
выполняется отдельной командой `uv run alembic upgrade head` после запуска PostgreSQL.
`uv.lock` фиксирует разрешённые версии зависимостей; коммитить его вместе с pyproject.toml.

## Структура

- `backend/app/api`, `schemas` — HTTP и валидация входных данных.
- `backend/app/planning` — чистый Python: модели и расчёт маршрута.
- `backend/app/integrations` — загрузка демонстрационных данных, затем адаптеры внешних API.
- `backend/app/db`, `alembic` — модели и миграции; первая миграция создаёт users и PostGIS.
- `data/demo.json` — синтетические POI и направленная матрица времени переездов.
- `docs/mvp.md` — правила и этапы реализации.
- `frontend` — Next.js + TypeScript: группы, предпочтения, поездки и результаты расчёта.

## Текущее поведение

Расчёт выполняется для одного дня в условном Demo City. День начинается в точке `start`.
Время — минуты от полуночи по местному времени, суммы — целые евроценты.
Бюджет общий для группы; стоимость POI умножается на число участников.
Учитываются ожидание открытия, длительность посещения и переезды. Возвращение
к месту проживания пока не моделируется. В результат включаются только посещения,
помещающиеся в бюджет и временные окна.

Обязательные POI имеют приоритет, затем используется средний вес категории по участникам.
При равенстве приоритетов порядок определяется ID для воспроизводимости.
Запрет относится к группе целиком. Конфликт запрета и обязательного POI возвращается явно.
При недостающем времени переезда переход считается недоступным.
Незапланированные обязательные POI делают результат `is_feasible=false`.
Неуспех greedy не доказывает отсутствие допустимого маршрута: далее нужен beam search.
Частичный маршрут при неуспехе возвращается только для диагностики.

Удовлетворённость — средний интерес участника к категориям посещённых POI,
число от 0 до 1; это начальная метрика, а не полная fairness-оптимизация.
Визы, погода, авторизация, Redis, LLM и альтернативы пока не реализованы.

## Выбор алгоритма

У обоих эндпоинтов расчёта есть query-параметры `algorithm=greedy|beam` и
`beam_width=1..128` (по умолчанию 32). Без параметров используется прежний greedy.
Пример расчёта для уже сохранённого запроса поездки:

```powershell
Invoke-RestMethod -Method Post -Uri 'http://127.0.0.1:8001/api/v1/trips/3/routes?algorithm=beam&beam_width=32'
```

Полный новый сценарий:

```powershell
.\scripts\demo-group.ps1 -BaseUrl http://127.0.0.1:8001 -Algorithm beam
```

В БД сохраняется `algorithm=beam-v1:w32`. Оба алгоритма проходят один независимый валидатор.
Beam search ограничивает число рассматриваемых состояний на каждом шаге шириной луча;
результат greedy также участвует в выборе, поэтому результат не хуже него по принятому
порядку оценки. Это эвристика без гарантии глобального оптимума или нахождения любого
существующего допустимого маршрута. Ограничение текущей реализации — 100 кандидатов POI.

Порядок выбора: выполнимость → число обязательных мест → суммарная полезность группы
→ минимальная индивидуальная накопленная полезность → меньшая стоимость → более раннее
окончание → порядок ID. Полезность — среднее по участникам от суммы весов категорий
всех посещений. Она отличается от `satisfaction`, которая нормирована числом посещений.
Первичный критерий полезности поощряет несколько посещений одной интересной категории;
модель разнообразия и полная fairness-оптимизация пока не реализованы.

Сравнение без БД из `backend`:

```powershell
.\.venv\Scripts\python.exe compare_algorithms.py
```

Методика и выводы: [docs/algorithm-comparison.md](docs/algorithm-comparison.md).
Машинный отчёт: `docs/algorithm-comparison.json`.

## Реальные POI: Лиссабон

В этой рабочей копии зависимость парсера расписаний установлена и миграция `0003`
применена. На другой машине сначала из `backend`:

```powershell
uv sync --locked
uv run alembic upgrade head
```

При запущенном API полный сценарий из корня:

```powershell
.\scripts\demo-group.ps1 -BaseUrl http://127.0.0.1:8001 -Algorithm beam -Destination Lisbon -TravelDate 2026-10-23
```

`GET /api/v1/destinations` показывает доступные направления.
`GET /api/v1/destinations/Lisbon/pois?travel_date=2026-10-23` возвращает каталог с именами,
координатами, источниками, расписанием и причинами исключения. Для сохранённого запроса
используй `destination=Lisbon` и `travel_date=YYYY-MM-DD`; прочие эндпоинты не меняются.

Дата нужна для проверки недельного расписания и исключений. При расчёте сохраняются
источники, время получения, имена, координаты POI, нормализованные окна и матрица
переездов в `result.data_context`. Результат сохраняется с `data_source=osm-osrm-lisbon-v1`.

Подробности и ограничения: [docs/real-data.md](docs/real-data.md).

## Инфраструктура

Данные БД сохраняются в Docker volume. Остановка без удаления данных:
`docker compose down`. Backend пока запускается локально для удобства разработки.
PostgreSQL доступен по `127.0.0.1:55432`, внутри контейнера используется порт 5432.
Redis, Celery, nginx и контейнер backend добавляются после первого сквозного сценария.
